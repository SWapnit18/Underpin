3. Bug Reports & Engineering Fixes

Bug 1: Task Completion Overwrites Existing Priority FIXED

Location: src/services/taskService.js:69 | Severity: High

Root Cause: The completeTask(id) function hardcoded priority: 'medium' upon task completion. If a user had created an urgent or low-priority task, completing it permanently erased and corrupted the priority value.

Resolution: Removed the hardcoded priority property so the existing task's attributes are fully preserved via object spread (...task).

Bug 2: Off-By-One Offset in Pagination Calculation FIXED

Location: src/services/taskService.js:12 | Severity: High

Root Cause: Offset was computed as offset = page * limit. When requesting page 1 with limit 2, offset evaluated to 1 * 2 = 2, skipping items 0 and 1 entirely.

Resolution: Corrected formula to (pageNum - 1) * limitNum with defensive numeric parsing (Math.max(1, parseInt(page) || 1)).

Bug 3: Loose Status Substring Matching

Location: src/services/taskService.js:9 | Severity: Medium

Root Cause: Status filtering used t.status.includes(status) instead of strict equality (===), allowing partial terms like status=do to match both todo and done.

Status: Formally documented with a diagnostic test in tests/taskService.test.js.

4. New Feature: Task Assignment Endpoint

Implemented endpoint: PATCH /tasks/:id/assign

Key Architectural Decisions

  • Input Validation (src/utils/validators.js): Validates that the assignee field is present, is a string, and contains non-whitespace characters. Rejects empty payloads with HTTP 400.
  • Conflict Protection (src/services/taskService.js): If a task already has an assignee, returns { conflict: true, task } which the route maps to HTTP 409 Conflict. This prevents race conditions and accidental overwrites in multi-user environments.
  • Resource Verification: If the target ID does not exist, returns HTTP 404 Not Found.

5. Production Readiness & Engineering Reflection

  1. Data Persistence: The current implementation relies on an in-memory array. Before production deployment, an ACID-compliant database (PostgreSQL with Prisma/Knex) should replace in-memory arrays to prevent data loss on server restarts.
  2. Concurrency & Race Conditions: In a high-throughput multi-worker setup, concurrent writes to the same task must be protected using database transactions or optimistic concurrency control (e.g. version tokens).
  3. Security & Auth: Add authentication (JWT / OAuth2), role-based access control (RBAC), Helmet security headers, and Express rate limiting.
